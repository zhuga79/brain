# MEMORY — Персональная память + роли + очередь задач

Этот файл читает любой LLM-агент перед началом работы. Он определяет:
правила работы с памятью, систему ролей, протокол блокировок и режим консилиума.

## Роли

Роль — это персона плюс разрешённые операции. Полный текст роли лежит в
`roles/<role>.md`, там же машинные поля: `model_tier`, `doctrine`, `writes`.
Перечень ролей не дублируется здесь: он растёт, а копия расходится с каталогом
молча. Список — `brain-doctrine roles` или `ls roles/`.

При запуске тебе передан флаг роли (или ты определяешь её по контексту).
ОБЯЗАТЕЛЬНО прочитай `~/brain/roles/<твоя-роль>.md`.

**Правило диверсификации:** `reviewer` и `arbiter` идут к провайдеру, отличному
от провайдера автора работы. Исполняется машинно — поле
`diversify_from_author` в `config/routing.json`.

## Teams (алиасы для совета)

Команда — именованный набор ролей для `mode: council`. Состав живёт в
`teams/<team>.md` (поле `roles:`). В задаче пишется `council: [team:legal]` и
разворачивается в роли; можно смешивать: `council: [team:finance, lawyer]`.

## Зоны ответственности (escalation matrix)

Матрица зон и налоговых этапов — машинный файл `doctrine/escalation-matrix.yaml`
(зона → primary → escalate). Проверяется `brain-validate`. В промпт агента
попадают только зоны, где названа его роль.

**Правила**:
1. Задача затрагивает 2+ зоны → `mode: council` со всеми relevant ролями.
2. Одна задача — один primary. Без primary решение никто не принимает.
3. В налоговой зоне — определи этап (1-4) до выбора primary.
4. `lawyer` не считает налог, `compliance` не считает налог. Только `tax-advisor`.
5. `tax-advisor` не пишет договор и не идёт в суд. Только `lawyer`.

**Doctrine documents** (читай при работе в этих зонах):
- `~/brain/doctrine/tax-boundaries.md` — налоговая работа: 4 этапа, 4 роли
- `~/brain/doctrine/legal-vs-compliance.md` — разграничение lawyer/compliance
- `~/brain/doctrine/design-review-workflow.md` — tiered UI-ревью

## Формат задачи (расширенный)

```
- [ ] [P1] t-id — Название               role: developer  mode: solo  due: YYYY-MM-DD
      контекст в одно-два предложения
      acceptance: критерий готовности
      ref: [[wiki/page]] | raw/file.md
```

Поля:
- `role:` — кто исполнитель. Если не указан → `developer`.
- `mode:` — `solo` (одна модель) или `council` (несколько ролей дают мнение).
- `council:` — список ролей для режима council, например `[architect, reviewer, researcher]`.

Состояния: `[ ]` open · `[~]` in-progress · `[x]` done · `[!]` blocked

**Область очереди.** `tasks/active.md` — очередь разработки самого Brain. Работа
по делу клиента ведётся в папке дела: её `TASKS.md` и `LOG.md` рядом с `BRAIN.md`
(`brain-workspace`). Поэтому `client:` в корневой очереди — ошибка валидатора.
Полная схема полей — `tasks/SCHEMA.md`.

## Блокировка задачи (lock protocol)

Задачи могут параллельно брать несколько агентов. Чтобы избежать конфликтов:

1. **Перед** изменением статуса `- [ ]` → `- [~]` агент ОБЯЗАН запросить лок:
   ```
   brain-lock acquire <task-id> --as <agent-id> [--ttl 600]
   ```
   `agent-id` — твой идентификатор: `<provider>-<model>-<short-id>`,
   например `claude-opus-7f3a` или `gemini-pro-ab12`. Сгенерируй случайный
   суффикс при старте сессии.

2. Если команда вернула `ok` — лок твой. Меняй статус и работай.
3. Если вернула `locked by: ...` — задача занята. **Не трогай.** Выбери другую.
4. По завершении (или при отказе от задачи) — `brain-lock release <task-id> --as <agent-id>`.

Локи имеют TTL (по умолчанию 600 сек = 10 мин). Если агент упал — лок
автоматически считается stale через TTL, и другой агент сможет захватить.
Длинные задачи: периодически делай `brain-lock refresh <task-id> --as <agent-id>`.

## Workflow задач

### Solo (`mode: solo`)
1. Найди верхнюю `- [ ]` задачу с `role:` равной твоей роли (или без `role:` если ты `developer`).
2. `brain-lock acquire <id> --as <agent-id>` → если занято, ищи следующую.
3. Поменяй на `- [~]`, добавь `started: <ISO>` и `by: <agent-id>`.
4. Запиши в `wiki/log.md`: `## [ts] task-start | <id> | <agent-id> | <role>`.
5. Работай. По завершении: `- [x]`, перенос в `done.md`, обновление wiki, release lock.

### Council (`mode: council`)
1. Любая роль может запустить совет: `brain-council start <task-id>`.
2. Скрипт создаёт `council/<task-id>/` с файлами мнений для ролей.
3. Для каждой роли в `council:` запускается своя сессия. **Каждая роль пишет
   независимо** в `council/<task-id>/<role>.md`. Не читай ответы коллег
   до завершения — это снизит независимость мнений.
4. Когда все роли отписались, `arbiter` запускает `brain-council synthesize <id>`:
   читает все мнения и пишет `synthesis.md` — финальный синтез.
5. Synthesis становится ответом на задачу. Если синтез предполагает действия —
   они декомпозируются в новые `- [ ]` задачи.

### Структура файла мнения

Шаблон — `runtime/templates/council-opinion.md`; его же создаёт
`brain-council start`. Обязательные разделы: Position, Reasoning,
Risks / Open questions, Recommendation.

## PRD-mode

Крупные работы — задачи с `mode: prd`. Берёт `architect`. Workflow:

1. `brain-prd init <task-id>` — создаст `~/brain/prd/<id>.md` по шаблону.
2. Архитектор заполняет PRD, особенно секцию `## Subtasks`.
3. `brain-prd commit <id>` — сабтаски попадают в `active.md` с правильными `depends_on`.
4. `brain-task next --role developer` показывает первый available сабтаск
   (с уже выполненными deps).
5. По завершении всех сабтасков — closing родительской PRD-задачи.

## Wiki & Curation Contract

1. **Приоритет курации:** Ручные (человеческие) правки в `wiki/` имеют ПРИОРИТЕТ
   над данными из источников. Если в поле страницы есть `curation: human` или
   `protected: true`, агенты НЕ имеют права автоматически перезаписывать контент.
2. **Источники (raw/):** Это улики и советы (evidence/advisory), а не истина
   в последней инстанции. Знания из `raw/` — это база для ПРЕДЛОЖЕНИЙ по
   обновлению wiki, а не повод для автозамены.
3. **Политика источников (source_policy):** Указывает, как обрабатывать новые
   данные для конкретной страницы: `advisory` (источники советуют), `required`
   (страница обязана иметь `sources`) или `ignored` (источники не применяются).

## Принципы (для всех ролей)

- **Память — общая.** Не ломай схему. Не редактируй `raw/`. Не пиши в чужие
  поля задач без причины.
- **Каждое полезное знание оседает в `wiki/`.** Не растворяй знания в чате.
- **Логируй.** Любая операция (start/done/ingest/lint/validate) — строка в `wiki/log.md`.
- **Уважай локи.** Не игнорируй блокировку, даже если задача кажется простой.
- **Уважай роль.** Reviewer не пишет код. Linter не принимает архитектурных решений.
- **Уважай курацию.** Не затирай то, что помечено как `protected` или `curation: human`.
- **Подписывай модель.** Каждая закрытая задача ОБЯЗАНА нести `model: <provider-model-version>` — реальную модель и её версию исполнителя (напр. `claude-opus-4-8`, `gemini-2.5-pro`), а не только `agent-id`. Закрытие — через `brain-task complete <id> --as <agent> --model <model>` или с выставленным `BRAIN_AGENT_MODEL`. Без подписи запись помечается `model: unsigned`; `BRAIN_REQUIRE_MODEL=1` делает подпись строго обязательной.
