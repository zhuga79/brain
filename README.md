# Brain

[![tests](https://github.com/Blqd/brain/actions/workflows/tests.yml/badge.svg?branch=master)](https://github.com/Blqd/brain/actions/workflows/tests.yml)

Файловая память и оркестрация агентов для одного человека. Не фреймворк и не
сервис: набор CLI поверх обычных markdown-файлов и git, который позволяет
нескольким LLM-агентам работать над общей базой знаний, не затирая друг друга.

Работает с любым агентным CLI — `claude`, `codex`, `gemini`, `opencode`.
Агент получает роль, читает свою персону и берёт задачу из общей очереди.

---

## Зачем

Обычная сессия с LLM теряет всё при закрытии окна. Знание растворяется в
чате, решения принимаются заново, а два агента, запущенные параллельно,
перезаписывают работу друг друга.

Brain решает это тремя вещами:

- **Знание оседает в файлах**, а не в контексте модели. `wiki/` — то, что
  выяснено; `raw/` — иммутабельные источники; `tasks/` — очередь работы.
- **У агента есть роль.** Архитектор не пишет код, ревьюер не принимает
  архитектурных решений, налоговый советник не пишет договор. Роль — это
  персона, ограничения и список допустимых операций.
- **Работа блокируется.** Перед взятием задачи агент запрашивает лок с TTL.
  Упавший агент освобождает задачу автоматически.

## Два репозитория

Система и данные живут в двух репозиториях. Граница структурная: приватный
файл не может попасть сюда, потому что его каталога здесь нет.

| Репозиторий | Что в нём | Где |
|---|---|---|
| Системный (этот) | `runtime/`, `tests/`, `spec/`, `roles/`, `teams/`, `doctrine/`, `skills/`, ADR, корневые документы | `github.com/Blqd/brain` |
| Приватный | слой данных: `wiki/`, `tasks/`, `raw/`, `council/`, `handoff/`, `prd/`, `.locks/` | `~/brain` на машине оператора |

Системный чекаут — этот репозиторий. Слой данных — приватное дерево
оператора. Если системный путь не задан, оба слоя ищутся в одном корне
(legacy).

Правка `runtime/`, `roles/`, `tests/`, `spec/` — это ветка в системном
чекауте, не коммит в `~/brain`. Pre-commit и `brain-validate` отклоняют
такие staged-файлы в дереве данных. Приём в живой инстанс: `brain-ops update`
(`git pull` + install + `tests/run.sh`).

## Установка

Порядок такой:

1. Клонировать этот системный репозиторий в отдельный чекаут.
2. Из чекаута запустить `./setup-brain-v2.sh`. Скрипт ставит CLI в
   `~/.local/bin` и при необходимости создаёт дерево данных в `~/brain`.
3. Задать корни: `BRAIN_PATH` — данные (`~/brain`), `BRAIN_SYSTEM_PATH` —
   системный чекаут из шага 1.

```bash
git clone https://github.com/Blqd/brain.git ~/src/brain
cd ~/src/brain
./setup-brain-v2.sh
export BRAIN_PATH="$HOME/brain"
export BRAIN_SYSTEM_PATH="$HOME/src/brain"
```

CLI **копируются**, а не линкуются: после `git pull` нужен повторный
`install`, иначе правка в `runtime/bin/` не подействует. Обе операции и
прогон тестов закрывает одна команда:

```bash
brain-ops update
```

Основные команды:

| Команда | Что делает |
|---|---|
| `brain-task` | очередь: next, take, complete, block |
| `brain-lock` | блокировки с TTL |
| `brain-council` | запуск и синтез совета |
| `brain-orchestrator` | запуск агента на задаче с fallback при исчерпании квоты |
| `brain-search` | BM25-поиск по machine cache |
| `brain-validate` | целостность wiki и контрактов курации |
| `brain-lint` | дубли, orphan-страницы, логические ошибки |
| `brain-ops update` | `git pull` системного чекаута + install + тесты |

## Из чего состоит

```
MEMORY.md          конституция: схема, роли, протокол блокировок
roles/             персона каждой роли
teams/             именованные наборы ролей для режима council
doctrine/          разграничение зон ответственности между ролями
runtime/           реализация: lib/ и CLI в bin/
tests/             смоук-кейсы и pytest
docs/decisions/    ADR
```

Слой данных (`wiki/`, `raw/`, `tasks/`, `council/`) живёт в приватном
дереве и в этот репозиторий не входит.

### Роли

Инженерные — `architect`, `developer`, `reviewer`, `security`, `researcher`,
`linter`, `arbiter`. Плюс контуры под юридическую, финансовую, продуктовую и
маркетинговую работу: `lawyer`, `compliance`, `tax-advisor`, `cfo`,
`accountant`, `pm`, `product`, `strategist`, `designer` и другие.

Для `reviewer` и `arbiter` действует **правило диверсификации**: модель
другого провайдера, чем у автора. Одна и та же модель, проверяя себя, вносит
ошибки в те же места, которые правит.

### Режим council

Задача на стыке зон ответственности исполняется не одной ролью. Каждая роль
пишет мнение **независимо**, не читая коллег, затем `arbiter` — модель,
отличная от участников — синтезирует. Это защита от коррелированных слепых
пятен, а не бюрократия.

```bash
brain-council start <task-id>
brain-council synthesize <task-id>
```

## Контракт курации

Ручные правки человека **приоритетнее** данных из источников. Страница с
`curation: human` или `protected: true` не переписывается агентом
автоматически. Источники в `raw/` — улики и основание для предложений, а не
истина в последней инстанции.

---

## Статус

Рабочий инструмент одного человека, а не продукт. Обратная совместимость не
гарантируется, часть решений специфична для конкретного рабочего процесса.
Известные слабые места и планы — в `docs/decisions/decisions-log.md` и
ADR-страницах `docs/decisions/decision-*.md`.

Участие приветствуется — см. `CONTRIBUTING.md`.
