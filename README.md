# Brain

[![tests](https://github.com/Blqd/brain/actions/workflows/tests.yml/badge.svg?branch=master)](https://github.com/Blqd/brain/actions/workflows/tests.yml)

Файловая память и оркестрация задач для людей и LLM-агентов, работающих над
общим вольтом. Не фреймворк и не сервис: набор CLI поверх обычных
markdown-файлов и git. Нет демона, нет базы, нечего хостить — всё состояние
это файлы, а значит оно диффится, форкается и сливается как исходный код.

Работает с любым агентным CLI — `claude`, `codex`, `gemini`, `opencode`.
Агент получает роль, читает свою персону и берёт задачу из общей очереди.
Небольшая группа (2–5 человек) может вести один вольт по git без потери
данных.

Подход опирается на идею [LLM wiki][llm-wiki] Андрея Карпати: агент ведёт
вики вместо того, чтобы в каждой сессии заново добывать знание с нуля. Brain
берёт этот инсайт и добавляет операционный слой, необходимый команде, — роли,
блокировки, ревью и федерацию.

[llm-wiki]: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

## Зачем

Обычная сессия с LLM теряет всё при закрытии окна. Знание растворяется в
чате, решения принимаются заново, а два агента, запущенные параллельно,
перезаписывают работу друг друга. В небольшой команде — у каждого свои
агенты — становится хуже: задача, которой никто не владеет, решение из одной
сессии, не долетевшее до другой, очередь, тихо разъехавшаяся на две.

Brain решает это четырьмя вещами:

- **Знание оседает в файлах**, а не в контексте модели. `wiki/` — то, что
  выяснено; `raw/` — иммутабельные источники; `tasks/` — очередь работы.
- **У агента есть роль.** Архитектор не пишет код, ревьюер не принимает
  архитектурных решений, налоговый советник не пишет договор. Роль — это
  персона, ограничения и список допустимых операций.
- **Работа блокируется.** Перед взятием задачи агент запрашивает лок с TTL.
  Упавший агент освобождает задачу автоматически.
- **Вольт синхронизируется по git.** Двое и больше людей делят один
  репозиторий; состояние сливается детерминированно, ничего не теряется при
  столкновении.

## Федерация: группа работает над общим списком задач

Федерация — это многопользовательский режим. Он позволяет 2–5 людям (плюс их
агентам) работать над одним общим git-репозиторием вольта, не затирая друг
друга.

- **Идентичность узла.** Каждый вольт называет себя сам (`BRAIN_NODE_ID` или
  `config/federation.json`), имя едет в каждой аудит-строке `wiki/log.md`.
  Фолбэк — `anonymous`, одиночный вольт ничего не отдаёт наружу.
- **Детерминированное слияние журнала.** `wiki/log.md` append-only;
  `brain-federation` ставит git-драйвер слияния, который берёт коммутативное
  объединение строк и дедуплицирует по `(ts, op, task_id, agent, node, extra)`.
- **Слияние очереди по id задачи, а не по позиции строки.** Когда два узла
  правят `tasks/active.md`, прогресс состояния побеждает (`done` >
  `in-progress` > `blocked` > open), односторонняя правка поля берётся, ни
  одна задача не теряется. Реальное расхождение (две конфликтующие правки,
  open↔done на одной задаче) блокирует sync чистым абортом, а не молчаливым
  затиранием.
- **Конфликт лока не разрешается молча.** Взять задачу, свежо занятую чужим
  узлом, нельзя; понижение чужого `in-progress` требует явного ревью.

```bash
brain-federation preflight   # что сломает sync
brain-federation sync        # pull --rebase с merge-драйверами, push
brain-sync-cycle --apply     # то же из systemd-таймера
```

Федерация адвайзори, а не распределённый lock-протокол: состояние несёт git,
правила слияния сводят параллельный цикл. Это осознанный компромисс для
малой команды на одном репозитории.

## Brain и конкуренты

Оркестраторов в этой нише несколько. Различия важнее пересечений.

| | **Brain** | **OpenClaw** | **ai-crew-sync** | **ShareClaw** |
|---|---|---|---|---|
| Состояние | **git + markdown** | демон + база данных | сервер Postgres | JSON + SQLite |
| Нужно запускать/хостить | **ничего** | демон | сервер (Postgres) | нет (но файлы БД) |
| Работает с | **любым агентным CLI** | обёртка CLI как движка | любым MCP-клиентом | любым файловым агентом |
| Мультипользователь | **git-федерация, 2–5** | фокус на одного оператора | общая шина (сервер) | только общая ФС |
| Лок задачи | mkdir-лок, TTL | владение сессией/worktree | lease, TTL | файловый лок |
| Ревьюер обязан быть **другого провайдера** | **да** | нет | нет | нет |
| Совет = независимые мнения, синтез **другой** моделью | **да** | голосование консенсусом | нет | голосование консенсусом |
| Человеческая курация главнее источников (`curation: human` / `protected`) | **да** | нет | нет | нет |
| Назначение | общий список задач + память | запускать кодинг-CLI одним движком | координационная шина команды | слой координации роя агентов |

Коротко:

- **OpenClaw** решает «запускать несколько кодинг-CLI как один runtime». Brain
  не оборачивает CLI вообще — он координирует агентов, которых вы уже
  запускаете, и его контракт — это файлы.
- **ai-crew-sync** требует сервер и базу для той же координации. У Brain
  координация — это и есть тот git-репозиторий, которому вы уже доверяете.
- **ShareClaw** ближе всех по духу (файловый слой координации), но хранит
  истину в JSON и SQLite. Brain держит всё в git, поэтому состояние
  синхронизируется, форкается и сливается как исходный код — и два вольта
  сходятся детерминированно, а не затирают друг друга.

Если демон и база для вашей команды нормальны — ai-crew-sync или OpenClaw
могут подойти лучше. Если вы хотите, чтобы общий список задач был просто
папкой в вашем репозитории — без сервиса, без состояния вне git и с ревью,
которое не использует ту же модель, что писала код, — Brain это другая форма.

## Два репозитория

Система и данные живут в двух репозиториях. Граница структурная: приватный
файл не может попасть сюда, потому что его каталога здесь нет.

| Репозиторий | Что в нём | Где |
|---|---|---|
| Системный (этот) | `runtime/`, `tests/`, `spec/`, `roles/`, `teams/`, `doctrine/`, `skills/`, ADR, корневые документы | `github.com/Blqd/brain` |
| Данные | слой данных: `wiki/`, `tasks/`, `raw/`, `council/`, `handoff/`, `prd/`, `.locks/` | `~/brain`, у каждого оператора / общий у команды |

Системный чекаут — этот репозиторий. Слой данных — приватное дерево
оператора (команды). Если системный путь не задан, оба слоя ищутся в одном
корне (legacy). `roles/` принадлежит системному чекауту: файл роли лежит в его
`roles/<role>.md`, перечень — `brain-doctrine roles`. В дереве данных
каталога `roles/` нет и быть не должно.

Правка `runtime/`, `roles/`, `tests/`, `spec/` — это ветка в системном
чекауте, не коммит в `~/brain`. Pre-commit и `brain-validate` отклоняют
такие staged-файлы в дереве данных. Приём в живой инстанс: `brain-ops update`
(`git pull` + install + `tests/run.sh`).

## Установка

```bash
git clone https://github.com/Blqd/brain.git ~/src/brain
cd ~/src/brain
./setup-brain-v2.sh
export BRAIN_PATH="$HOME/brain"
export BRAIN_SYSTEM_PATH="$HOME/src/brain"
```

Скрипт ставит CLI в `~/.local/bin` и при необходимости создаёт дерево данных
в `~/brain`. Роли резолвятся из `$BRAIN_SYSTEM_PATH/roles/<role>.md`;
перечень — `brain-doctrine roles`. Debian-пакет собирается
`runtime/packaging/build-deb.sh` (см. `docs/deb-install-runbook.md`).

Установщики (`setup-brain-v2.sh`, `add-*-brain.sh`, `install-*.sh`,
`patch-brain-run-doctrine.sh`, `refine-tax-boundaries.sh`) и `pyproject.toml`
живут **только** в системном чекауте, и запускать их можно только оттуда.
Копия в `~/brain` не безобидна: тогда `SCRIPT_DIR` совпадает с корнем данных,
setup считает установку однокорневой, пересоздаёт `roles/`, `doctrine/`,
`skills/`, `config/` и перезаписывает ваш `MEMORY.md` шаблоном.
`brain-validate` и pre-commit write-path guard отклоняют такие копии
с указанием канонического файла.

CLI **копируются**, а не линкуются: после `git pull` нужен повторный
`install`, иначе правка в `runtime/bin/` не подействует. Обе операции и
прогон тестов закрывает одна команда:

```bash
brain-ops update
```

Основные команды:

| Команда | Что делает |
|---|---|
| `brain-task` | очередь: next, take, complete, block |
| `brain-lock` | блокировки с TTL |
| `brain-council` | запуск и синтез совета |
| `brain-federation` | многопользовательский sync: preflight, plan, sync, merge-tasks, merge-log |
| `brain-orchestrator` | запуск агента на задаче с fallback при исчерпании квоты |
| `brain-search` | BM25-поиск по machine cache |
| `brain-validate` | целостность wiki и контрактов курации |
| `brain-lint` | дубли, orphan-страницы, логические ошибки |
| `brain-ops update` | `git pull` системного чекаута + install + тесты |

## Из чего состоит

```
MEMORY.md          конституция: схема, роли, протокол блокировок
roles/             персона каждой роли
teams/             именованные наборы ролей для режима council
doctrine/          разграничение зон ответственности между ролями
runtime/           реализация: lib/ и CLI в bin/
tests/             смоук-кейсы и pytest
docs/decisions/    ADR
```

Слой данных (`wiki/`, `raw/`, `tasks/`, `council/`) живёт в дереве данных и
в этот репозиторий не входит.

### Роли

Инженерные — `architect`, `developer`, `reviewer`, `security`, `researcher`,
`linter`, `arbiter`. Плюс контуры под юридическую, финансовую, продуктовую и
маркетинговую работу: `lawyer`, `compliance`, `tax-advisor`, `cfo`,
`accountant`, `pm`, `product`, `strategist`, `designer` и другие.

Для `reviewer` и `arbiter` действует **правило диверсификации**: модель
другого провайдера, чем у автора. Одна и та же модель, проверяя себя, вносит
ошибки в те же места, которые правит.

### Режим council

Задача на стыке зон ответственности исполняется не одной ролью. Каждая роль
пишет мнение **независимо**, не читая коллег, затем `arbiter` — модель,
отличная от участников — синтезирует. Это защита от коррелированных слепых
пятен, а не бюрократия.

```bash
brain-council start <task-id>
brain-council synthesize <task-id>
```

## Контракт курации

Ручные правки человека **приоритетнее** данных из источников. Страница с
`curation: human` или `protected: true` не переписывается агентом
автоматически. Источники в `raw/` — улики и основание для предложений, а не
истина в последней инстанции.

---

## PRD-режим

Крупные работы — задачи с `mode: prd`. Берёт `architect`. Workflow:

1. `brain-prd init <task-id>` — создаёт `~/brain/prd/<id>.md` по шаблону.
2. Архитектор заполняет PRD, особенно секцию `## Subtasks`.
3. `brain-prd commit <id>` — сабтаски попадают в `active.md` с правильными
   `depends_on`.
4. `brain-task next --role developer` показывает первый available сабтаск
   (с уже выполненными deps).
5. По завершении всех сабтасков — closing родительской PRD-задачи.

## Статус

Рабочее ПО с живым циклом релизов: системный слой как публичный репозиторий,
`.deb`-сборка на CI, смоук + pytest до установки. Инструмент рассчитан на
одного оператора или небольшую команду (2–5 человек) на одном общем вольте.
Обратная совместимость не гарантируется, часть решений специфична для
конкретного рабочего процесса. Известные слабые места и планы — в
`docs/decisions/decisions-log.md` и ADR-страницах
`docs/decisions/decision-*.md`.

Участие приветствуется — см. `CONTRIBUTING.md`.
